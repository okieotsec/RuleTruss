# Security frameworks: NIST SSDF and MITRE SAF

How RuleTruss's security practice lines up with two public frameworks, what evidence backs each claim, and what is still open.

- **NIST SSDF** ([SP 800-218, version 1.1](https://csrc.nist.gov/projects/ssdf)) is a catalogue of secure software development practices.
- **MITRE SAF** ([Security Automation Framework](https://saf.mitre.org/framework/)) is a way to organise security automation into five capabilities: Plan, Harden, Validate, Normalize and Visualize.

**This is the developer's own assessment of a small, pre-release project, written with AI assistance. It is not an audit, and nothing here is a certification or a claim of compliance.** Every status points at a file you can read. Where the repository cannot show something (a setting on GitHub, for example), the table says so. SSDF 1.2 is an initial public draft (December 2025) with no final version yet; this page follows 1.1 and will be re-mapped when 1.2 is final.

Last reviewed: 2026-10-14, checkpoint [CP9](../reports/cp9-security-framework/claude.md).

## MITRE SAF

SAF describes five capabilities. RuleTruss is a local tool, so some of them have little to do here.

| Capability | What it means here | Status |
| --- | --- | --- |
| **Plan** | Security requirements: the threat model and scope in the test plan, and SECURITY.md. SAF's Vulcan tool authors STIG-style requirement documents for platforms; this project has no such platform baseline, so it is not used. | Met |
| **Harden** | SAF's hardening content configures deployed systems. The equivalent here is the application's own secure defaults (see PW.9) and hardening the build pipeline: pinned actions, least-privilege tokens, zizmor, Scorecard, a seven-day Dependabot cooldown. | Met for the application and pipeline; N/A for hosts |
| **Validate** | Automated checks with a pass/fail gate: the test suite, the hostile-input set and the scanners. SAF's own validation uses InSpec profiles, which test the configuration of a host or service. An InSpec-compatible profile could assert the "loopback only" and file-mode claims at run time; it is not written (see open items). | Met |
| **Normalize** | [tools/security_checks.py](../tools/security_checks.py) writes SARIF for ruff, semgrep, gitleaks, osv-scanner and bandit, and if the SAF CLI is installed converts each to the Heimdall Data Format (HDF) under `hdf/` in the checkpoint folder. | Met, optional |
| **Visualize** | `saf view summary` output is archived as `saf-summary.txt`; the `hdf/*.json` files open in SAF's Heimdall viewer. | Partly: Heimdall was not exercised in CP9 |

### Using the SAF CLI

The SAF CLI is optional. Nothing in the build, the tests or CI needs it, and the release gate does not depend on it.

```
npm install --prefix ~/.cache/saf @mitre/saf          # about 480 packages: keep it out of the project and out of CI
SAF_CLI=~/.cache/saf/node_modules/.bin/saf .venv/bin/python tools/security_checks.py reports/cpN-name
```

Without it the runner prints `saf (optional)  NOT RUN` and carries on. When present, it converts each SARIF file to HDF and runs `saf validate threshold -I "{failed.total.max: 0}"` on it.

Two things to know:

- **Suppressed results are removed before conversion.** semgrep reports in-source suppressions in its SARIF; SAF would count them as failures. They are not hidden: each one is in `suppressions.json` and must be in the reviewed baseline.
- **Ignore SAF's "compliance" percentage.** These tools report problems, not a list of controls, so with no findings SAF shows 0 controls and 0%. The threshold on failed results is the meaningful check.

## Owner checklist: settings the repository cannot show

These are GitHub settings, to be done when the repository is published. Until then the related practices stay at Partly.

- [ ] Two-factor authentication on the account that owns the repository.
- [ ] A branch ruleset on `main`: pull request required, status checks required (Tests, Lint, Secret scan, Workflow audit, CodeQL, OSV), force pushes and deletion blocked.
- [ ] Private vulnerability reporting enabled (SECURITY.md tells people to use it).
- [ ] Dependabot alerts and security updates, secret scanning and push protection enabled.
- [ ] Code scanning: use the CodeQL workflow in this repository, not GitHub's "default setup" as well.
- [ ] Actions settings: default token permission read-only, and "require actions to be pinned to a full-length commit SHA".
- [ ] Decide whether to publish Scorecard results (`publish_results` in security.yml is `false`) and whether to apply for the OpenSSF Best Practices badge, which is a free self-assessment.

## Open items, in order

1. Independent review before any public release (PO.2, PW.2, PW.7): required by the release gate.
2. Review the local history before publishing anything (PS.1).
3. Dynamic scan of the local web server with OWASP ZAP, in a container, using a throwaway token (PW.8).
4. Atheris on the capture and configuration parsers for a release candidate (PW.8).
5. A release workflow with build provenance, once there is something to release (PS.2, PS.3).
6. Optionally, an InSpec-compatible profile (Cinc Auditor is the free build) that asserts loopback binding and file modes (SAF Validate).
7. Tick the owner checklist; re-map to SSDF 1.2 when NIST finalises it.
